# Architecture Decision Log

This document captures architectural decisions that aren't immediately obvious from the code.
Record decisions here when future-you might ask _"why did I do it this way?"_.

---

## System-wide

| Decision                                    | Rationale                                                                                                                    |
| ------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| Use `datetime` (not `float`) for timestamps | Human-readable when debugging; PostgreSQL `TIMESTAMPTZ` has powerful time functions; Python `datetime` can be timezone-aware |
| Always use timezone-aware UTC               | Avoids ambiguity; consistent across systems; required for `TIMESTAMPTZ`                                                      |
| Use `Decimal` for live trading money        | Precision matters for real transactions; `float` is fine for backtesting where speed > precision                             |

## Data System

| Decision                                                                    | Rationale                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| --------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Denormalise `bot_id` on `bot_ticks`                                         | Read performance is critical for time-series data; avoids JOIN on `bot_runs` for common query _"all ticks for bot X"_; enables partitioning                                                                                                                                                                                                                                                                                                                                                           |
| Composite primary key `(trade_id, pair)` on `trades`                        | Kraken trade IDs are only unique within a trading pair                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| Dual backend (SQLite + PostgreSQL)                                          | SQLite for fast local backtesting; PostgreSQL/Supabase for durable cloud storage from the live-trading process on Fly.io                                                                                                                                                                                                                                                                                                                                                                              |
| `SupabaseConfig` uses metaclass properties (lazy env var reading)           | Class-level `os.getenv()` calls are evaluated at import time, before `load_env()` runs in scripts. Metaclass `@property` defers reading until attribute access (i.e., inside `SupabaseClient.__init__`), so scripts can import `data_system` in normal order without needing deferred imports.                                                                                                                                                                                                        |
| Repositories own both serialisation directions (`_to_record` + `_to_*`)     | Type conversion between domain types (`UUID`, `datetime`, `Decimal`, enums) and DB-compatible primitives belongs exclusively in the repository layer. Domain models stay clean; consumers always work with typed domain objects. Shared logic extracted into `_to_record()` (domain → DB) and `_to_*()` (DB → domain) private methods for symmetry.                                                                                                                                                   |
| `DECIMAL(32, 12)` is sufficient precision for live trading `Decimal` fields | Schema supports 12 fractional digits; Kraken prices (1–2 dp), volumes, fees, and balances (4–8 dp) never come close. Two precision loss effects were confirmed harmless in testing: (1) PostgreSQL silently truncates values beyond 12 dp — only triggered by artificially extreme test data; (2) PostgREST serialises `NUMERIC` as JSON `number` (float64), which can lose the 12th decimal place — a difference of at most `0.000000000001`, irrelevant for GBP-denominated trading. No fix needed. |
| `bots.id` is a human-readable TEXT primary key (not UUID)                   | Bots are referenced by stable handles like `robo` or `btc_1m_v1` in the `BOT_IDS` env var, `fly deploy` workflows, and log lines. A UUID PK would force every operational surface to look up names indirectly and would make `bot_ticks.bot_id` (denormalised) effectively opaque. The trade-off — needing to pick a unique handle when registering a bot — is cheap.                                                                                                                                 |
| `bot_orders.tick_id` is nullable and back-filled                            | Orders are persisted with `placed_at` immediately on submission so a crash between exchange-call and tick-persist can never lose them. The corresponding `bot_tick` row is written afterwards, then the order is updated with its `tick_id`. Nullability is the natural representation of this ordering — the FK is real but late-bound.                                                                                                                                                              |

## Trade Executor

| Decision                                                          | Rationale                                                                                                                                                                                                                                                                                                       |
| ----------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Always-on process over stateless invocations                      | EMAs are IIR filters and never fully converge from a cold start; warming up once and keeping state in memory eliminates per-interval seed bias (most consequential at crossover boundaries) and halves the per-interval Kraken API footprint.                                                                   |
| APScheduler `BlockingScheduler` + `CronTrigger` + `:05` offset    | Wall-clock alignment fires at `:00`, `:05`, … matching candle close — `IntervalTrigger` would drift relative to candles. 5s offset accounts for Kraken data propagation lag. `BlockingScheduler` integrates cleanly with signal handlers via `shutdown(wait=True)`.                                             |
| `misfire_grace_time=1` and `max_instances=1`                      | Trading safety: never queue or stack a missed interval. APScheduler 3.x treats `misfire_grace_time=0` as "infinite grace" — `1` is the correct value for "discard if late".                                                                                                                                     |
| `jitter=3` on the cron trigger                                    | Prevents N bots in one process from hitting Kraken at the exact same instant.                                                                                                                                                                                                                                   |
| Removed `IntervalContext` — private methods on `TradeExecutor`    | Was too thin to justify as a class. Transformation logic (`_fetch_ohlc`, `_fetch_balances`) lives directly on the executor — less indirection, one fewer class.                                                                                                                                                 |
| DB-registered bots over CLI-args                                  | Adding a bot is a `bots` table insert + `BOT_IDS` update + `fly deploy`; no code changes. Strategy params, pair, interval, and version are all owned by Supabase.                                                                                                                                               |
| Per-bot `BotRun` lifecycle                                        | A `BotRun` row is created on construction and marked complete on graceful shutdown. `completed_at IS NULL` is the canonical "this run crashed" signal — no extra schema needed.                                                                                                                                 |
| Warm-up via abstract `Strategy.warmup_candles` property           | Each strategy declares its own warm-up requirement from its configured indicator windows. Changing windows in `strategy_configs.py` automatically adjusts the requirement — no executor changes.                                                                                                                |
| Skip persisting ticks during warm-up                              | Warm-up signals are mathematically incomplete (EMA hasn't converged). Recording them would pollute the decision log with unreliable data.                                                                                                                                                                       |
| Warn-and-continue on insufficient warm-up candles                 | New trading pairs may have fewer than `warmup_candles` of history. Refusing to start would prevent them from ever running; logging a warning surfaces the issue without blocking.                                                                                                                               |
| Kraken's 720-candle OHLC cap is a known limitation                | Kraken's OHLC endpoint returns at most 720 candles and does not paginate. `_fetch_ohlc_history()` requests `min(warmup_candles, 720)`. `PrecisionTrendStrategy` maxes at 237; an Optuna-optimised `SmaStrategy` with `long_window > 719` would be partial-warmed. Solving via stored local trades is deferred.  |
| State recovery from latest **directional** tick (BUY/SELL only)   | `strategy.last_action` is only ever BUY or SELL — it drives consecutive-signal suppression. Recovering from a HOLD tick would corrupt suppression and could cause double-buys. The repository query filters `signal IN ('buy', 'sell')` at the SQL layer.                                                       |
| Reverse `last_action` if associated order FAILED                  | If the latest directional tick's order failed on the exchange, the position never actually changed — set `last_action` to the opposite signal so the bot doesn't try to exit a position it never entered.                                                                                                       |
| `PositionSizer` abstraction (default `AllInPositionSizer`)        | Injectable component; replicates current behaviour. Unblocks Kelly, volatility-scaled, or partial-fill sizers without touching `TradeExecutor`.                                                                                                                                                                 |
| `PairBalances` frozen dataclass over a dict                       | Bundles `symbol_base` / `symbol_quote` with `balance_base` / `balance_quote` so symbol lookup never escapes the executor; field names align with `BotTick.balance_base`/`balance_quote` and avoid ambiguity between symbols and amounts.                                                                        |
| One bot per currency pair (current constraint)                    | `AllInPositionSizer` assumes exclusive access to the pair's balance (BUY → full quote, SELL → full base). Two bots on the same/overlapping pairs would compete. A future `BalanceAwarePositionSizer` could partition; not needed today.                                                                         |
| `BotOrder` lifecycle: `PLACED → FILLED \| FAILED`                 | Persist immediately on submission with status PLACED + `placed_at` (crash-safe). Confirm fills via `QueryOrdersConnector` (3× retry in-interval) and reconcile any leftover PLACED orders at the start of every interval. No order ever stays in limbo.                                                         |
| Separate `placed_at` and `filled_at` (renamed from `executed_at`) | `placed_at` records submission directly on the order, independent of tick persistence. `filled_at` records when the fill confirmation arrived — meaningful for both FILLED and FAILED orders.                                                                                                                   |
| `exchange_order_id` (domain) vs `txid` (connector)                | Kraken uses `txid` for order IDs, distinct from the trade IDs and ledger IDs visible in the UI. The connector layer keeps `txid` (matches the Kraken API); the domain layer renames to `exchange_order_id` for self-documenting schema reads. Mapping happens in `TradeExecutor`.                               |
| `QueryOrdersConnector` for fill data                              | `BotOrder` requires `Decimal` price/volume/fee. Estimated values would compromise the data integrity the schema is designed for. Multiple txids fit in one Kraken request — N PLACED orders cost one API call.                                                                                                  |
| Per-interval order reconciliation                                 | Naturally handles slow market fills today and unblocks limit orders later (which may take minutes/hours to fill or cancel) without further changes.                                                                                                                                                             |
| Partial error ticks                                               | OHLC failure: skip the tick (price is non-nullable). Strategy/order failure: persist the tick with `error` set so nothing is lost. Clean data in `bot_ticks` — every row has real values.                                                                                                                       |
| Graceful drain shutdown                                           | `request_shutdown()` flips an internal flag; `scheduler.shutdown(wait=True)` blocks for in-flight jobs; `shutdown()` marks the run complete. Prevents interrupted order placements on `fly deploy`. Public `request_shutdown()` keeps the flag mutation behind an API rather than touching a private attribute. |
| Dry run via Kraken `validate=True`                                | Kraken validates pair/volume/balance for free without placing an order. Dry-run mode logs ticks instead of persisting them — persisting would corrupt `recover_state()` when switching to live (the bot would think it holds a position it never bought).                                                       |
| Post-trade balance recording on BUY/SELL intervals                | The tick reflects the bot's actual position **after** acting on its signal — useful for downstream analysis without a join.                                                                                                                                                                                     |
| Post-suppression signal stored in `BotTick`                       | Records what the bot actually did, not what the strategy raw output was. Recovery and audits both want the acted-on value.                                                                                                                                                                                      |
| `Bot.strategy_version` is metadata only                           | Stored in `bots` for auditing ("which version was this bot running?"). Not used by `create_strategy()` or the executor at runtime.                                                                                                                                                                              |
| Health monitoring via `bot_ticks` timestamps                      | `MAX(timestamp) FROM bot_ticks GROUP BY bot_id` is the heartbeat query. No schema changes required; gaps surface real OHLC failures via `fly logs`.                                                                                                                                                             |
| Text logging now, JSON deferred; `LOG_LEVEL` env var override     | Adequate for `fly logs` during initial deployment. Switch to JSON in a one-line formatter change when a log sink (Datadog/Loki) is added. `LOG_LEVEL` toggles app-package loggers without redeploying.                                                                                                          |

## Cloud Platform

| Decision                                              | Rationale                                                                                                                                                                                                                                                                                                                                                                    |
| ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Fly.io over AWS Lambda                                | Always-on warm indicators, half the per-interval API calls, and far less operational surface (one Dockerfile + `fly.toml` vs Lambda + ECR + EventBridge + IAM + CloudWatch + Terraform). ~$2/month is cheap enough that the simplicity wins outright.                                                                                                                        |
| Fly.io over a self-managed VPS                        | `fly deploy` is simpler than managing OS updates, SSH, systemd, and monitoring on a VPS for comparable cost ($2-3/month vs $4-6/month).                                                                                                                                                                                                                                      |
| Single process for N bots (for now)                   | 2-5 bots have a negligible memory footprint together. Migrates naturally to Fly.io Machines API (one container per bot) at 10+ bots — only the entry-point script changes.                                                                                                                                                                                                   |
| No `[http_service]` block in `fly.toml`               | Fly.io's machine auto-stop behaviour only applies to HTTP-fronted services. Omitting the block keeps the always-on outbound-only trading process running continuously without needing an explicit `auto_stop_machines = false`.                                                                                                                                              |
| `kill_timeout = 60` in `fly.toml`                     | Gives the SIGTERM handler enough time to drain in-flight intervals (including `_confirm_order`'s 3s retry window) before SIGKILL — preventing orders that were placed on the exchange but not persisted.                                                                                                                                                                     |
| Nanosecond Kraken nonce + serialised private dispatch | APScheduler's thread pool can issue two private requests in the same millisecond. A class-level lock on `KrakenApiClient` guards the `time.time_ns()` + `max(now, last + 1)` nonce step **and** the request dispatch — strictly increasing nonces alone aren't enough; Kraken returns `EAPI:Invalid nonce` if requests arrive out of order, so the lock spans the full POST. |
| One `SupabaseClient` instance per `TradeExecutor`     | The Supabase SDK's underlying `httpx` client is not safe for concurrent writes from multiple scheduler threads. Per-executor clients sidestep shared-state issues — constructed once in `start_scalping.py` per bot.                                                                                                                                                         |

## Exchange Connector

| Decision                                         | Rationale                                                                                                                                                                                                                                                                                             |
| ------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Three-layer architecture (API/Service/Connector) | Separates HTTP concerns from business logic from public interface; enables mocking at each layer for testing                                                                                                                                                                                          |
| Retry with exponential backoff                   | Kraken rate limits are strict; automatic retries with backoff prevent failures during high-volume operations like bulk trade fetching                                                                                                                                                                 |
| Optional client injection in connectors          | Allows default instantiation for production use while enabling mock injection for tests                                                                                                                                                                                                               |
| Domain object conversion in connectors           | Connectors are the boundary between external API and internal domain; keeps raw API formats out of business logic                                                                                                                                                                                     |
| Keep connector layer despite simple delegation   | Connectors provide platform-agnostic interface for future multi-exchange support; even thin wrappers add strategic value by establishing stable public API and natural home for domain logic                                                                                                          |
| Add domain models only when necessary            | Not all connectors need domain objects; add them when they provide value (type safety, transformation logic, multi-exchange abstraction, persistence preparation). Balance abstraction with pragmatism.                                                                                               |
| Exchange models in `exchange_connector/models/`  | Domain models representing exchange API responses live in `exchange_connector/models/` as they're exchange-specific concepts, not database entities. Exception: if raw API response exactly matches database schema (like `Trade`), the model can live in `data_system/models/` to avoid duplication. |

## Backtesting Engine

| Decision                                                       | Rationale                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Use Optuna for parameter optimisation                          | TPE sampler provides efficient Bayesian optimisation; built-in parallelization via PostgreSQL storage; pruning reduces wasted trials; proven in ML hyperparameter tuning with similar search spaces                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Rolling 3-month windows with 1-month steps                     | 3 months provides sufficient data for diverse market conditions; 1-month overlap increases sample density; warmup day allows indicators to initialize; longer windows reduce noise, shorter steps increase out-of-sample coverage                                                                                                                                                                                                                                                                                                                                                                                               |
| Geometric mean for multi-window aggregation                    | Accounts for compounding effects (returns multiply, not add); penalises inconsistency more than arithmetic mean; one bad window significantly impacts score, encouraging robust strategies                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| Logistic activity penalty (0.3 trades/day ideal)               | Empirical finding: ~1 trade per 3 days balances opportunity vs fees; logistic curve provides smooth gradients for Optuna; avoids hard thresholds that create optimisation cliffs; caps at 1.0 to avoid penalising high activity                                                                                                                                                                                                                                                                                                                                                                                                 |
| Concurrent Optuna with constant_liar sampler                   | Enables parallel trial execution without lock contention; constant_liar prevents trials from exploring duplicate regions; multivariate=True captures parameter correlations; group=True improves convergence speed                                                                                                                                                                                                                                                                                                                                                                                                              |
| Two-phase evaluation (optimise → evaluate OOS), not combined   | Optuna's TPE sampler relies on a consistent objective; mixing in-sample and out-of-sample into one score muddies what's being sampled and slows convergence. Running OOS on every trial would also multiply compute for trials that are never inspected — the top-N filter in `evaluate_out_of_sample` exists precisely so OOS cost is paid only on parameter sets worth a closer look. Separate phases also support walk-forward analysis and clean reporting of "which parameter sets generalise vs which merely fit training data".                                                                                          |
| "Optimisation" (operation) vs "evaluation" (data scope) naming | "Optimisation" stays as the _operation_ name on the in-sample side — it's an Optuna parameter search, not passive evaluation — so `optimise_parameters` is unchanged. "In-sample" and "out-of-sample" are _data-scope_ qualifiers used where parallel naming aids comprehension, hence `evaluate_out_of_sample` (was `find_params`). Library code, schema (`out_of_sample_evaluation`), and docs follow the same convention.                                                                                                                                                                                                    |
| OOS stores no whole-period money column                        | Earlier versions ran a redundant full-period backtest and stored its `final_balance` alongside `oos_balance_ratio`. Dropped: an arithmetic mean of window balances carried no orthogonal information beyond `oos_balance_ratio` (just a less-conservative restatement of the same vector), and _compounding_ overlapping 3-month windows would be misleading. OOS rows now store only `oos_balance_ratio`, computed on the same rolling windows used during in-sample optimisation so scores are directly comparable.                                                                                                           |
| OOS parallelism: `ProcessPoolExecutor`, one engine per worker  | OHLC load + resample is the dominant fixed cost per worker, so each worker constructs its own `BacktestingEngine` once and iterates its assigned chunk of parameter sets — rather than per-task submission, which would re-load OHLC for every parameter set. Process-based concurrency (not threads) because the per-tick path is CPU-bound on pandas/NumPy and would not benefit from the GIL-bound thread pool already used by Optuna inside `optimise_parameters`.                                                                                                                                                          |
| Factory-based strategy creation in optimisation                | Backtesting engine uses `create_strategy(type(strategy).__name__, params)` instead of `type()` reconstruction; single source of truth for strategy creation; eliminates coupling between engine and strategy/config class hierarchy                                                                                                                                                                                                                                                                                                                                                                                             |
| Optuna mutates `engine.strategy` per trial                     | `BacktestingEngine` is constructed with one `Strategy` instance, but the objective replaces `engine.strategy` via `create_strategy(name, params)` for every trial. The constructor strategy is just a seed — it carries the class identity (so the factory knows which strategy to rebuild) and validates that the engine can be set up before optimisation starts. Avoids the alternative of either threading a class reference through the constructor or rebuilding the engine per trial (which would re-load and re-resample OHLC every time).                                                                              |
| Dual computation modes (vectorised + iterative)                | Iterative mode tests the same code path used in live trading (row-by-row with stateful indicators), ensuring strategies behave identically in production; vectorised mode uses pandas operations for 10-100x speedup during optimisation; debugging step-through is a secondary benefit                                                                                                                                                                                                                                                                                                                                         |
| Store studies in PostgreSQL not SQLite                         | PostgreSQL supports concurrent writes from parallel workers; row-level locking prevents conflicts; connection pooling improves throughput; SQLite would serialise all trial writes                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| 0.4% fee on both sides                                         | Matches Kraken Pro spot taker fees (0.4%) — assumes worst case since live execution uses market orders that cross the book; applied symmetrically to buy and sell for simplicity (maker fee is 0.25% but not relied on); fee tier may drop with volume but conservative default avoids over-optimistic backtests                                                                                                                                                                                                                                                                                                                |
| OOS verdict: combined floor + drawdown, not absolute-only      | A pure OOS floor catches trials that lose money outright but misses ones that look great in-sample and only fall apart out-of-sample (e.g. `3.0 IS / 1.1 OOS` clears any reasonable floor). A pure delta misses trials where both numbers are bad but the gap is small. Combined rule (`oos < floor OR is - oos > drawdown_limit`) catches both failure modes. False-positive cost is cheap (one ignored trial); false-negative cost is real money if a brittle strategy is deployed.                                                                                                                                           |
| OOS row persists `is_value` alongside `oos_balance_ratio`      | The combined verdict rule depends on both IS and OOS values. `is_value` lives in Optuna storage by default; rather than join the OOS table against Optuna at every page render, the IS value is captured at OOS evaluation time and persisted on the row. Tradeoff: tiny data duplication (Optuna trial values are write-once, so no drift risk) for single-query aggregation (`aggregate_windows` stays one SQL round-trip), cleaner repository abstraction (no Optuna handle leaking in), and rows that survive study deletion intact.                                                                                        |
| IS and OOS are not strictly symmetric (penalty asymmetry)      | IS applies a logistic activity penalty (`[0, 1]`) for under-trading; OOS does not. So `is_value` is dragged down by the penalty while `oos` is not, biasing the IS→OOS delta negative even for non-overfit strategies. The OOS verdict's drawdown side therefore biases conservative (under-flags); the floor side is unaffected. Accepted rather than fixed because applying the penalty on OOS would either require recomputing per-window trade counts at evaluation time or back-filling historical rows — neither cheap and the asymmetry's effect is small in practice when top trials already trade near the ideal rate. |

## Strategy Manager

| Decision                                                             | Rationale                                                                                                                                                                                                                                                                             |
| -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Dual computation modes (live + vectorised)                           | Live mode (row-by-row) is what runs in production, so backtesting must support it to verify identical behaviour; vectorised mode uses pandas operations for 10-100x speedup during parameter optimisation; debugging step-through is a secondary benefit                              |
| Indicators/Rules/Strategies as mutable classes                       | Live trading requires maintaining state between updates (EMA values, price windows); immutable dataclasses inappropriate for evolving state                                                                                                                                           |
| Accept code duplication between modes                                | Each algorithm implemented twice (stateful vs vectorised); maintenance burden accepted for performance benefits; comprehensive tests ensure parity                                                                                                                                    |
| Use `Signal` enum from `data_system`                                 | Type safety across modules; IDE autocomplete; string-compatible for backward compatibility; centralised definition prevents drift                                                                                                                                                     |
| Bounded state with `deque(maxlen=N)`                                 | Prevents unbounded memory growth in 24/7 live trading; only store what's needed (window size); constant memory footprint per strategy instance                                                                                                                                        |
| Strategy-specific config DTOs on initialisation                      | Strategies take frozen dataclass configs (e.g., `PrecisionTrendStrategyConfig`) instead of individual parameters; enables type safety, IDE support, and single source of truth for parameter validation                                                                               |
| Config `__post_init__` validation instead of `constraints()` methods | Constraints enforced in config dataclasses eliminate duplication; same validation applies in backtesting and live trading; ValueError caught during optimisation and converted to `optuna.TrialPruned`; single source of truth                                                        |
| `reset()` on indicators and strategies                               | Separates state resetting from re-parameterisation; enables strategy reuse across backtest windows without full reconstruction; backtesting engine uses factory for new params and `reset()` for same-params-different-window; rules remain stateless by design and have no `reset()` |

## Walk-Forward UI

| Decision                                                          | Rationale                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Studies rail summary is Optuna-only — OOS lives in the panel      | Rail rows show `trial_count` + `best_is` from `StudySummary` so each row is a 1:1 reflection of the study's optimisation state. OOS scores are window-scoped (one set per OOS window per trial), and a single rail row can't faithfully summarise an "OOS verdict" without picking a window — and that pick belongs to the user. The OOS panel's tab strip handles per-window selection; pushing the choice back to the rail would either force an arbitrary window or duplicate the panel's UI on every row.                                                                                                                                                                                                 |
| In-process Optuna study cache with explicit invalidation contract | `load_study` caches loaded `optuna.Study` instances in a module-level dict because reloading on every render (study switch, window click, copy-params, refresh) would be sluggish — each load is multiple PostgreSQL round-trips. The price is staleness: Optuna's `_CachedStorage` view inside the loaded `Study` lags the database when IS workers persist trials in another process, or when the UI sits idle. The cache is therefore paired with `invalidate_study_cache(name)` and a contract: invalidate before any read that should reflect newly-persisted trials. Concrete call sites: `OosPanel._refresh_data` (study switch + manual refresh), every IS-timer tick, the page's phase-done handler. |
| IS-run live timer refreshes the OOS panel only                    | The 5 s timer activated during an in-sample run scopes its work to `OosPanel.refresh()`. Per-trial progress already streams to the IS panel's worker grid via the PROGRESS callback, so the IS panel needs no polling. The rail row's `trial_count`/`best_is` are accurate at run start and at run end; refreshing them mid-run would just thrash the rail without surfacing anything useful (live counts climb in the worker grid). The OOS panel's top-N trials view is the only fragment whose contents genuinely become stale as IS workers persist new trials, so the timer is narrowly scoped to it.                                                                                                    |
